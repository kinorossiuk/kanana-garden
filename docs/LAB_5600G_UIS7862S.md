# 5600G · Codex · UIS7862S 테스트 랩

## 역할과 데이터 흐름

```text
GitHub Public
  └─ source, tests, issue, OTA metadata
          │ clone/push
          ▼
현재 작업 폴더 + Codex ───── API test ───▶ 5600G 모델 서버 (:8000)
          │                                      Kanana 1.3B / CPU
          │ adb doctor/capture
          ▼
UIS7862S 테스트 헤드유닛
  └─ OTA 적용, 앱/시스템 재현, logcat/dumpsys/screenshot
```

원칙은 다음과 같다.

1. 모델 가중치와 추론은 5600G에만 둔다.
2. 테스트 코드, 캡처 분석, 수정 작업은 현재 작업 폴더에서 수행한다.
3. UIS7862S는 테스트 대상이다. 모델 서버나 Git 저장소 역할을 맡기지 않는다.
4. 소스와 이슈는 GitHub Public에 저장한다. OTA 바이너리와 원본 진단 번들은 Git에
   넣지 않는다.
5. OTA 버전, Android build fingerprint, 앱 버전, Git commit을 한 재현 건에
   함께 기록한다.

## 1. 현재 작업 폴더 준비

Python 3.10 이상과 Android platform-tools의 `adb`가 필요하다.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .

cp .env.example .env
# .env의 KANANA_BASE_URL, KANANA_API_KEY를 실제 값으로 변경

make test
make github-check
```

`.env`, `reports/uis7862s/`, `var/`는 Git에서 제외된다. API 키, OTA 바이너리,
위치·계정·차량 정보가 포함될 수 있는 원본 캡처를 실수로 올리지 않기 위한
경계다.

## 2. 5600G 모델 서버

5600G 호스트에서 이 저장소를 clone한 뒤 실행한다.

```bash
./ops/5600g/install.sh

sed -n '1,200p' ~/.config/kanana-garden/server.env
# KANANA_API_KEY와 HF_HOME을 수정

./ops/5600g/run.sh
```

초기 기준은 Ryzen 5 5600G의 6개 물리 코어와 CPU `float32`다. 1.3B 가중치만
float32로 약 5.2 GB이므로 OS와 생성 중 임시 메모리를 포함해 RAM 16 GB 이상을
권장한다. `auto`나 `bfloat16`은 정확성·속도·메모리 기준선을 별도로 얻은 뒤
채택한다. 서버는 한 모델 인스턴스의 생성을 직렬화해 동시 요청에 따른 메모리
급증과 성능 측정 오염을 피한다.

상시 실행은 user systemd unit으로 구성할 수 있다.

```bash
mkdir -p ~/.config/systemd/user
cp ops/5600g/kanana-garden.service ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now kanana-garden

systemctl --user status kanana-garden
journalctl --user -u kanana-garden -f
```

`0.0.0.0`에 바인딩하면 API 키가 필수다. 방화벽에서도 현재 분석 PC의 주소만
8000/tcp에 접근하도록 제한한다. 외부 공개 추론 서버로 사용하지 않는다.

분석 PC에서 연결을 확인한다.

```bash
make server-doctor
kanana-garden check meeting-action-items-ko \
  --output reports/5600g-meeting-action-items.json
```

## 3. UIS7862S 테스트 장비

벤치 전원에서 USB 디버깅을 켜고 분석 PC의 RSA 키를 승인한다. ADB TCP 연결을
쓸 경우 테스트 VLAN이나 격리된 유선망에서만 열고, 작업이 끝나면 끈다.

```bash
adb devices -l
make device-doctor
```

펌웨어에 따라 SoC가 `UIS7862S`가 아니라 내부 플랫폼명 `UMS512`로 노출될 수
있어 두 값을 모두 같은 프로필로 인식한다. 여러 장치가 연결되면 `.env`의
`ANDROID_SERIAL`로 대상을 고정한다.

버그를 재현한 직후 다음 명령을 실행한다.

```bash
make capture CAPTURE_ARGS='--label github-issue-12 \
  --package com.example.app --ota-version 2026.08.1'
```

기본 캡처에는 다음이 들어간다.

- 전체 logcat 링버퍼와 package/PID 중심의 필터 사본
- CPU, 메모리, 프로세스, 저장공간, 배터리, 열 상태의 dumpsys/proc 자료
- 현재 화면 PNG
- 식별 속성을 가린 getprop와 해시 기반 장치/부팅 ID
- crash, ANR, OOM/LMK, watchdog, thermal 후보를 뽑은 `analysis.json`
- 각 파일의 크기와 SHA-256을 기록한 `manifest.json`

전체 Android bugreport가 꼭 필요할 때만 `--bugreport`를 추가한다. bugreport와
logcat, 화면에는 개인정보가 들어갈 수 있으므로 외부 공유 전에 사람이 직접
검토한다.

## 4. OTA 보관과 검증

OTA 다운로드 URL과 SHA-256은 서로 독립적으로 확인한 공급자 릴리스 정보에서
가져온다. 값은 `.env`에 두고 다음과 같이 다운로드한다.

```bash
make ota-download

kanana-garden ota-verify var/ota/2026.08.1/manifest.json
```

다운로드는 임시 파일에 스트리밍되고 SHA-256이 일치할 때만 최종 파일명으로
바뀐다. 기본 저장소는 Git에서 제외된 `var/ota/<version>/`이며 manifest의
상태는 `downloaded-not-flashed`다.

자동 플래시는 제공하지 않는다. UIS7862S 헤드유닛은 판매자·MCU·보드별 복구
절차가 달라 잘못된 이미지를 자동 적용하면 복구 불능이나 차량 기능 장애로
이어질 수 있다. 적용 전에 최소한 다음을 확인한다.

- 대상 보드/판매자/MCU가 릴리스 대상과 정확히 일치한다.
- 현재 버전으로 되돌릴 수 있는 이미지와 복구 절차가 있다.
- `ota-verify`가 통과한다.
- 벤치 전원이 안정적이며 실차 주행 중이 아니다.
- 적용 전후 각각 `uis7862s-capture`를 남긴다.

## 5. GitHub Public 버전 관리

공개 저장소는 `https://github.com/kinorossiuk/kanana-garden`이다. `main`에
push하거나 pull request를 만들면 `.github/workflows/ci.yml`이 Python 3.10과
3.12에서 asset 검사, 리포트 재검산, 카탈로그 drift 검사와 전체 단위 테스트를
실행한다.

```bash
git remote -v
git status --short --branch
git push origin main
```

OTA 바이너리, `.env`, 원본 UIS7862S 캡처는 공개 저장소에 올리지 않는다. 이슈에
증빙이 필요하면 사람이 검토하고 비식별화한 최소 로그 구간, manifest SHA-256,
OTA version, build fingerprint와 관련 commit만 첨부한다.

## 6. 한 버그의 표준 루프

1. GitHub에 UIS7862S bug 템플릿으로 이슈를 만든다.
2. OTA를 `ota-verify`하고 벤치에서 적용한다.
3. `uis7862s-doctor` 결과의 build fingerprint를 이슈에 기록한다.
4. 문제를 3회 재현하고 재현율을 기록한다.
5. 즉시 `uis7862s-capture --label <issue-id> --ota-version <version>`을 실행한다.
6. Codex에 캡처 디렉터리와 기대/실제 결과를 주고 `analysis.json` 후보부터
   logcat 전후 문맥, dumpsys 상태 순으로 분석시킨다.
7. 회귀 테스트와 수정 코드를 같은 commit에 넣고 GitHub 이슈에 연결한다.
8. 수정 전후 캡처의 OTA, build fingerprint, app version, commit이 명시됐는지
   확인하고 이슈를 닫는다.
